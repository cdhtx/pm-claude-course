Part 01 · What Is It

Claude Code is Claude in your terminal

Claude.ai is a chat window. Claude Code is Claude with hands — it can read your files, write code, run commands, and build working software, all from a conversation in your terminal. You describe what you want, it builds it, shows you the changes, and asks if you want to keep them.

Think of it less like an AI chatbot and more like a brilliant engineer sitting next to you — one who never gets tired, never judges your questions, and can go from your raw idea to a working prototype faster than you can finish your coffee.

Agentic Terminal

Claude with full access to your file system. Reads, writes, runs, and builds. Shows you every change before it's permanent. This is where you build things.

Developer Integration

For building Claude into your own products. Requires coding knowledge. Not where you start — where you graduate to.

The key difference

Claude.ai answers questions. Claude Code takes actions. When you ask it to "build a dashboard," it actually builds one — creates the files, writes the code, and shows you the result. You stay in control by reviewing and approving every change before it's saved.

Part 03 · The Workflow

Three prompts. One working product.

This is the three-phase workflow that takes you from a rough idea to something real. Each phase has one core prompt. The key insight: don't skip phases. Brainstorming first makes the tech spec better. A good tech spec makes the build dramatically faster and cleaner.

Phase 1
🧠 Brainstorm
Pressure-test your idea. Get Claude to poke holes, ask hard questions, and sharpen the concept before any code is written.
Phase 2
📋 Tech Spec
Turn the sharpened idea into a precise technical blueprint. This is what Claude Code will build from — specificity here pays off enormously.
Phase 3
🏗️ Build
Hand Claude the spec and let it build. Review each change it proposes. Accept what's right. Redirect what isn't.
Why this order matters

Jumping straight to "build me an app" produces generic, brittle results. The brainstorm + spec combo gives Claude the context it needs to make good decisions throughout the build — what to prioritize, what to skip, what "done" looks like. 80% planning, 20% execution. The spec is your contract with Claude.

Part 04 · Phase 1

The Brainstorm Prompt

Use this before any code is written — even before you open Claude Code. This can happen in Claude.ai or at the start of a Claude Code session. The goal: stress-test your idea and arrive at a clear, specific concept before building anything.

🧠
Phase 1 of 3 · Brainstorm
The Idea Pressure-Tester
Run this before a single line of code is written
What it does
Claude plays three distinct roles: a curious potential user (who reveals real pain), a skeptical engineer (who reveals what's actually hard to build), and a strategic advisor (who reveals if this is the right problem to solve at all). You get three perspectives in one conversation.
Why it's token-efficient
Structured three-role format prevents rambling. "One question at a time" keeps the conversation moving without wasting tokens on unsolicited advice. The final output is a single crisp paragraph — not a 10-page report.
Prompt 1 · Brainstorm
I have an idea I want to build. Before we write any code, I need you to pressure-test it with me. Play three roles — one at a time, clearly labeled: 🙋 USER: A real person who has this problem. Ask me one probing question about whether this actually solves a pain you feel day-to-day. Be honest if the solution sounds like a solution looking for a problem. ⚙️ ENGINEER: Someone who has to build this. Ask me one question about scope, complexity, or a technical assumption I might be making that could blow up the timeline. 🎯 ADVISOR: A strategic product thinker. Ask me one question about whether this is the right problem to solve, the right time to solve it, and whether I'm the right person to build it. After I respond to all three, give me: — A sharpened one-paragraph version of my idea that incorporates what you've learned — The single biggest risk I should resolve before building — A go / no-go recommendation with one sentence of reasoning My idea: [describe your idea in plain language — as rough as you like]

you> I want to build a dashboard that shows PMs their key product metrics in one place, pulling from PostHog, Stripe, and Linear
Claude 🙋 USER:

Will your dashboard tell me what matters, or just show me numbers?"
⚙️ ENGINEER:
"PostHog, Stripe, and Linear each have different auth models and rate
limits. Are you building this for one PM's setup, or does it need to
work across different API keys for different users?"
🎯 ADVISOR:
"Datadog, Grafana, and Metabase all do parts of this. What's the
insight or workflow you're delivering that those tools don't?"

Claude ─── Sharpened idea:
A single-user PM pulse dashboard that pulls from PostHog, Stripe, and
Linear, surfaces anomalies automatically, and tells you what to do

Part 05 · Phase 2

The Tech Spec Prompt

Once your idea is sharp, turn it into a technical blueprint. This prompt takes the sharpened idea from Phase 1 and produces a spec precise enough for Claude Code to build from without constantly asking clarifying questions. Run this in Claude.ai or Claude Code — then save the output as SPEC.md in your project folder.

📋
Phase 2 of 3 · Tech Spec
The Blueprint Generator
Paste in your sharpened idea from Phase 1 — the more specific, the better
What it does
Translates a product idea into a builder-ready spec with a chosen tech stack, clear screens, data model, and explicit out-of-scope constraints. The [ASSUMED] flag forces Claude to surface its assumptions so you can correct them before the build starts.
Why save it as SPEC.md
When you start the build in Phase 3, you'll tell Claude Code to read SPEC.md. This gives it persistent context for the entire build session — it won't forget what you agreed on, and it won't invent features you didn't ask for.
Prompt 2 · Tech Spec
Turn the following product idea into a technical spec I can hand to an AI coding agent to build from. The spec must include: PRODUCT NAME & ONE-LINE DESCRIPTION TECH STACK: Choose the simplest stack that works — prefer HTML/CSS/JS for simple tools, React for interactive dashboards, Python for data/backend tasks. State your choice and why. SCREENS / VIEWS: List every screen or page. For each, describe what the user sees and what actions they can take. Be specific. DATA MODEL: What data does the app store or display? Where does it come from? INTEGRATIONS: Any external APIs or services? List with auth method. MVP CONSTRAINTS: What is explicitly OUT of scope for version 1? SUCCESS CRITERIA: How do we know the app is working correctly? (2-3 testable statements) OPEN QUESTIONS: Flag any decision I need to make before building starts with [NEEDS DECISION]. Flag any assumption you make with [ASSUMED]. Keep each section concise — this spec should fit on 2 pages. My product idea: [paste your sharpened idea from the brainstorm, or describe it fresh]

[ASSUMED] Single-user, no backend needed — API keys stored locally.

Save the spec as a file

After Claude generates the spec, copy it and save it as SPEC.md inside your project folder. In Phase 3, you'll start Claude Code and say "read SPEC.md and build this." That one file becomes the source of truth for the entire build.

Part 06 · Phase 3

The Build Prompt

Now you're in Claude Code — the terminal. You have your SPEC.md saved in the project folder. This is the prompt that kicks off the actual build. Claude will read the spec, plan its approach, and start writing files. This is where you'll be reviewing and accepting changes — more on that in the next section.

🏗️
Phase 3 of 3 · Build
The Build Kickoff
Run this inside Claude Code, in your project folder, with SPEC.md present
What it does
Tells Claude to read the spec first (so it has full context), plan before it acts (so you can review the plan), build incrementally (so changes are manageable), and check in at logical milestones rather than disappearing for 20 minutes and returning with 50 changed files.
The "check in" instruction
This is critical for beginners. Without it, Claude Code will sometimes build entire features in one sweep. The check-in instruction forces natural pause points where you can redirect, ask questions, or say "actually, skip that part" — without losing control of the build.
Prompt 3 · Build (run inside Claude Code terminal)
Read SPEC.md first, then build this application. Before writing any code: 1. Confirm you've read the spec by summarizing what we're building in 3 bullet points 2. Tell me the order you'll build things in (e.g., structure first, then UI, then data connections) 3. Flag any [NEEDS DECISION] items from the spec and wait for my answers Then build incrementally: — Set up the project structure first and show me before proceeding — Build one screen or feature at a time — After each major piece, show me what it looks like and what works — Check in before starting anything that touches external APIs or data If you're unsure about anything, ask — don't assume and build the wrong thing. When you're done with each section, tell me: what's working, what's next, and what I should test.

Part 07 · Staying in Control

When to accept changes

This is the part that trips up new users most. Claude Code always asks before changing your files — it shows you what it wants to do and waits for your approval. Here's the mental model for what to approve and what to push back on.

The golden rule

Read before you accept. Claude Code will show you exactly what files it's creating or changing. You don't need to understand every line — but you should know what it's building and why. If something surprises you, ask before accepting.

⏸ Pause and read first

🔴
It's changing a file that already exists and has content — especially config files like package.json, .env, or any file you didn't know about
🔴
It's about to run a terminal command (install packages, start a server, delete files) — read the command carefully before saying yes
🔴
It mentions touching an API with real credentials — make sure it's using test/sandbox mode first
🟡
The list of changed files is long (10+) — ask Claude to explain what each section does before accepting the whole batch
🟡
Something in the plan changed from what you discussed — ask "wait, why are you doing X?" before proceeding

✅ Safe to accept

✅
New files being created from scratch in a project you just started — these don't overwrite anything
✅
UI/styling changes to components that Claude just created in this same session — low risk, easy to undo
✅
Installing standard packages (React, Tailwind, Recharts) — these are well-known libraries you've seen in the spec
✅
Changes that match exactly what Claude told you it was going to do in its plan — no surprises means low risk
✅
Adding test data or placeholder content — this is how Claude proves the UI works before wiring up real data

Your safety net: git

Claude Code works best when you're using git — a tool that tracks every version of your files. If you accept a change and it breaks something, you can always roll back. Claude Code will often initialize git automatically; if it doesn't, type git init at the start of any project.

Your safety commands
# Save current state (do this after any working milestone) git add . git commit -m "working dashboard shell" # If something breaks and you want to undo the last changes git diff # see what changed git restore . # undo all uncommitted changes (back to last save) # Ask Claude to explain any command before running it you> what does this command do before I run it?

First session checklist

  • Phase 1 complete — idea is sharp, biggest risk identified
  • SPEC.md saved in project folder with all sections filled in
  • All [NEEDS DECISION] items resolved before build starts
  • Claude confirmed it read the spec before writing any code
  • First git commit made after project scaffold is created
  • UI visible with mock data before any real API connections
  • Reviewed at least one change with [v]iew before accepting
  • Something is working — celebrate, then iterate

Three prompts. One working product.

The fastest way to learn Claude Code is to build something you actually want. Pick your smallest useful idea — a personal dashboard, a tool that saves you 30 minutes a week, a prototype for your next pitch — and run the three prompts.
